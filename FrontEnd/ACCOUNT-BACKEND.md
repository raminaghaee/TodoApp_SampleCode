# تغییرات لازم در بک‌اند حساب کاربری (.NET)

فرانت‌اند آماده است و از سرور اختصاصی فعلی شما استفاده می‌کند؛ سرویس جدیدی جایگزین آن نشده است. تا پیاده‌سازی مسیرهای زیر، عملیات جدید در حالت API کار نمی‌کنند. در حالت نمایشی فقط شبیه‌سازی محلی انجام می‌شود و ایمیلی ارسال نمی‌شود.

## قرارداد دقیق درخواست‌ها

همه مسیرها با `/api/v1` شروع می‌شوند. درخواست‌های محافظت‌شده با کوکی HttpOnly فعلی و `credentials: include` ارسال می‌شوند؛ نام فیلدهای JSON دقیقاً مانند جدول باشد.

| عملیات | مسیر | بدنه | پاسخ موفق |
|---|---|---|---|
| ذخیره نام نمایشی | `PUT /api/v1/profiles/me` | `{ "display_name": "رامین" }` | `200`، کاربر کامل `{ "id": 1, "email": "user@example.com", "display_name": "رامین", "role": "user" }` |
| تغییر رمز از پروفایل | `POST /api/v1/auth/change-password` | `{ "current_password": "...", "new_password": "..." }` | `204` |
| درخواست تغییر ایمیل | `POST /api/v1/auth/change-email` | `{ "new_email": "new@example.com", "current_password": "...", "redirect_url": "https://your-app/confirm-email" }` | `200`، `{ "message": "لینک تأیید ارسال شد." }` |
| فراموشی رمز | `POST /api/v1/auth/forgot-password` | `{ "email": "user@example.com", "redirect_url": "https://your-app/reset-password" }` | همواره `200`، `{ "message": "اگر حساب موجود باشد، لینک ارسال می‌شود." }` |
| بازنشانی رمز | `POST /api/v1/auth/reset-password` | `{ "token": "...", "new_password": "..." }` | `204` |
| تأیید ایمیل جدید | `POST /api/v1/auth/confirm-email` | `{ "token": "..." }` | `204` |

سه مسیر آخر باید `[AllowAnonymous]` باشند؛ reset فقط توکن معتبر بازیابی را قبول می‌کند و **رمز فعلی نمی‌گیرد**. سه مسیر اول `[Authorize]` باشند؛ شناسه کاربر را از هویت تأییدشده بگیرید، نه از بدنه درخواست.

## تغییرات سرویس و ذخیره‌سازی

1. **نام نمایشی:** در اکشن فعلی `profiles/me` فقط `display_name` را به‌روز کنید؛ تغییر مستقیم `email`، `role` یا `id` از این مسیر ممنوع باشد. نام کاربری تغییر نمی‌کند. اعتبارسنجی طول نام با قواعد فعلی پروژه شما انجام شود.
2. **رمز پروفایل:** رمز فعلی را با password hasher فعلی بررسی کنید؛ در صورت خطا `400 ProblemDetails` با `detail: "رمز فعلی اشتباه است."` بدهید. رمز جدید را طبق سیاست فعلی سرور اعتبارسنجی و hash کنید. رمز خام هرگز ذخیره یا لاگ نشود. دیگر refresh sessionها را باطل کنید؛ نشست جاری را با کوکی جدید حفظ کنید تا کاربر همچنان وارد باشد.
3. **تغییر ایمیل:** رمز فعلی را بررسی کنید؛ ایمیل را normalize و یکتایی آن را با index پایگاه داده تضمین کنید. ایمیل جدید را به‌صورت pending نگه دارید؛ تا تأیید آدرس جدید، ایمیل قبلی و ورود با آن فعال بماند. لینک به ایمیل جدید و هشدار درخواست تغییر به ایمیل قبلی ارسال شود.
4. **فراموشی رمز:** پاسخ عمومی یکسان برای ایمیل موجود/ناموجود بدهید؛ حساب را افشا نکنید. لینک فقط به ایمیل واقعی ثبت‌شده و تأییدشده ارسال شود. در صورت خطای عمومی سرویس ارسال، پیام مناسب بدهید؛ پاسخ موفق را پیش از پذیرفته‌شدن ارسال جعل نکنید.
5. **توکن‌ها:** توکن تصادفی رمزنگاری‌شده بسازید، فقط hash آن را ذخیره کنید؛ فیلدهای لازم `UserId`, `TokenHash`, `Purpose`, `ExpiresAt`, `UsedAt`, `PendingEmail`. انقضا، یک‌بارمصرف‌بودن و purpose را بررسی کنید. مصرف توکن و تغییر داده باید در تراکنش انجام شوند تا دو درخواست همزمان نتوانند یک توکن را مصرف کنند. با ایجاد درخواست جدید، توکن قبلی همان کاربر/هدف را باطل کنید.
6. **پس از reset:** تمام نشست‌های کاربر و refresh tokenها را باطل و کوکی فعلی را پاک کنید؛ ورود خودکار انجام ندهید. **پس از تأیید ایمیل:** یکتایی را دوباره بررسی و ایمیل هویت ورود و پروفایل را یکجا به‌روز کنید؛ نشست‌ها را باطل و کوکی را پاک کنید تا کاربر با ایمیل جدید وارد شود.

اگر ASP.NET Core Identity دارید، از `ChangePasswordAsync` برای تغییر با رمز فعلی استفاده کنید؛ برای بازیابی از `GeneratePasswordResetTokenAsync` و `ResetPasswordAsync`، و برای ایمیل از `GenerateChangeEmailTokenAsync` و `ChangeEmailAsync` استفاده کنید. علاوه بر Identity، ثبت hash/مصرف اتمیک توکن لازم است تا لینک‌های تأیید قابل استفاده مجدد نباشند؛ در صورت استفاده از ایمیل به‌عنوان UserName آن را نیز در همان جریان امن همگام کنید.

## لینک ایمیل

لینک‌ها مطابق زیر باشند؛ توکن URL-encode شود:

```text
https://your-app/reset-password#type=recovery&token=ENCODED_TOKEN
https://your-app/confirm-email#token=ENCODED_TOKEN
```

فرانت توکن را از fragment (یا برای سازگاری از query) می‌خواند و از نوار آدرس حذف می‌کند. مسیرهای `/reset-password` و `/confirm-email` باید روی میزبان فرانت به اپلیکیشن برسند. توکن یا لینک کامل را در لاگ، ابزار تحلیل یا پاسخ API واقعی قرار ندهید؛ `demo_url` فقط در داده نمایشی وجود دارد.

`redirect_url` را به‌صورت آزاد قبول نکنید: scheme/origin/path را با فهرست مجاز تنظیم‌شده سمت سرور تطبیق دهید، از جمله نشانی واقعی فرانت و localhost توسعه. زمان انقضا و سیاست رمز را مطابق سیاست امنیتی خودتان تعیین کنید.

## امنیت و خطاها

- از HTTPS، کوکی‌های Secure/HttpOnly، SameSite مناسب و سیاست ضد-CSRF (بررسی Origin مجاز و JSON برای mutationها یا توکن ضد-CSRF هماهنگ با کلاینت) استفاده کنید؛ CORS با originهای مشخص و AllowCredentials، نه wildcard.
- rate limit برای درخواست و مصرف لینک و آزمون رمز فعلی اعمال کنید.
- وضعیت‌های مناسب: `400` برای رمز فعلی/توکن/اعتبارسنجی، `409` ایمیل تکراری، `401` برای نشست نامعتبر، `429` محدودیت درخواست.
- خطاها به شکل ProblemDetails فعلی شما با `detail` قابل‌فهم ارسال شوند؛ فرانت همان پیام را نشان می‌دهد و ورودی ناموفق حفظ می‌شود.
- هیچ پاسخ پروفایل یا login نباید password hash، توکن بازیابی، ایمیل pending یا سایر داده‌های حساس را برگرداند.

## آزمون‌های ضروری سرور

- کاربر فقط نام نمایشی خودش را تغییر دهد؛ تغییر نقش/ایمیل مستقیم نپذیرفته شود.
- رمز فعلی اشتباه هیچ تغییری ایجاد نکند؛ رمز قبلی پس از تغییر دیگر معتبر نباشد.
- ایمیل تا تأیید تغییر نکند؛ ایمیل تکراری، توکن منقضی/مصرف‌شده و توکن متعلق به purpose دیگر رد شوند.
- بازیابی برای موجود/ناموجود پاسخ عمومی یکسان بدهد؛ مصرف همزمان توکن تنها یک موفقیت داشته باشد.
- پس از reset یا تأیید ایمیل، ورود مجدد و ابطال نشست‌های قبلی بررسی شود.
